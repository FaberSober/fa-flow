# ADR：自定义表单多流程复用

- 状态：已采纳，F-FF-01、F-FF-02、F-FF-08 ✅已完成；日期：2026-10-03。
- 范围：`fa-flow/` 与 `frontend/apps/admin/features/fa-flow-pages/`。
- 目标：先跑通一张自定义表单供多个流程使用，再完善同一业务记录的多次流程及统一入口。
- 业务对象边界：本文方案适用于通用自定义表单，不绑定订单等具体业务。`ff_demo_order`、`ff_demo_order_goods` 仅作为测试表和截图示例，不要求新增订单专用实体、流程规则或代码分支。

## 功能开发说明

### F-FF-01 多流程引用同一表单

- 复用流程配置页面的“自定义表单”选择；流程 A、B 均可保存为同一 `formId`。
- 表单页面的关联流程改为只读列表，通过 `FlowProcess.formId` 查询；不增加另一份绑定关系。
- 移除 `FlowProcessBiz.validateCustomForm` 根据 `FlowForm.flowProcessId` 拒绝其他流程的限制。
- 验收：两个流程选择同一表单，保存重开；表单侧能看到两个关联流程。

#### 开发与验证记录（2026-10-03）

- 已移除 `validateCustomForm` 的旧反向单流程限制；继续校验表单存在、启用状态、设计类型及数据配置。
- 表单编辑页“关联流程”改为只读列表，复用流程列表接口按 `FlowProcess.formId` 查询自定义流程；支持加载失败重试，每次打开重新查询。
- 不再从表单编辑页配置 `flowProcessId`，保留旧字段；旧绑定不在当前关联列表时提示管理员检查，不自动修正配置。
- 自动验证：`mvn -pl fa-flow -am test-compile -DskipTests` 通过；独立运行 `FlowProcessSharedFormTest` 通过，覆盖两个流程复用同一旧绑定表单、无旧绑定及非法配置拒绝。
- 前端定向 Biome 检查：排除原有点击容器的 `noStaticElementInteractions` 问题后通过。TypeScript 检查受现有配置及 `@fa/ui` 类型入口缺失阻塞，未确认类型检查通过；未运行完整构建。
- 人工验收：
  1. 准备一张已启用、配置完整的自定义设计表单，分别在流程 A、B 配置中选择该表单并保存、发布；重开确认两者仍引用同一表单。
  2. 打开该表单的编辑弹窗，确认“关联流程”同时展示 A、B 的名称与 key，且不可在表单侧修改绑定；保存重开后列表仍正确。
  3. 将 B 改为另一张表单并保存，重开原表单编辑弹窗，确认只展示 A；再恢复 B 的配置，确认列表恢复两个流程。
  4. 若有旧 `flowProcessId` 指向其他表单的历史数据，确认显示不一致提示；若旧绑定指向当前关联的 A，则不应提示冲突，也不应阻止 B 保存、发布。
- 2026-10-07：用户确认 F-FF-01 人工验收通过，状态更新为 `✅已完成`。当时 F-FF-02、F-FF-03 尚未实施；F-FF-02 后续进度见下文。

### F-FF-02 共享表单发起闭环

- 沿用“流程审批 → 发起流程”页面，先选择流程，再加载该流程引用的自定义表单及开始节点配置。
- 每次首次成功发起新增一条主表及对应子表数据，启动所选流程并写入该条记录的 `flow_instance_id`。
- 成功后反馈并刷新；业务失败或请求失败保留输入，重试沿用已有幂等机制。
- 验收：从 A、B 分别填写同一表单并发起，得到两条业务记录和两个正确的流程实例；失败重试不重复新增。

#### 开发与验证记录（2026-10-07）

- 发起接口返回业务失败时，保留当前表单和请求幂等键；只有成功响应才关闭发起面板、刷新任务数并清空共享表单，避免下一流程误带上一条记录的值。
- 后端已在同一事务中保存主/子表数据、启动所选流程并写入 `flow_instance_id`；本次沿用已有事务和幂等实现。
- 人工验收：
  1. 确认流程 A、B 均已启用并引用同一张配置完整的自定义表单；进入“流程审批 → 发起流程”，分别打开 A、B，确认各自展示开始节点配置的表单。
  2. 填写 A 并提交，确认成功提示、发起面板关闭且任务数刷新；在表单数据中确认新增一条主表记录及其子表数据，`flow_instance_id` 指向 A 的实例。
  3. 再填写 B 并提交，确认表单未带入 A 的值；在同一业务表确认新增第二条记录及子表数据，`flow_instance_id` 指向 B 的实例。
  4. 用 Chrome DevTools Network Local Overrides 将 A 的首次 `/api/flow/manage/flowProcess/start` 响应临时改成非成功业务响应（请求仍正常到达服务端），确认发起面板和值保留；关闭覆盖后立即重试，核对两次请求的 `requestId` 相同，且表单数据中仅新增一条记录、仅创建一个实例。
- 2026-10-07：用户确认 F-FF-02 人工验收通过，状态更新为 `✅已完成`。

### F-FF-03 记录对应实例追踪

- 表单“数据”入口展示共用业务表中的记录，复用已完善的查询、列格式和显示配置。
- 流程信息按记录的 `flow_instance_id` 读取；查询和详情不再以 `FlowForm.flowProcessId` 作为判断依据。
- 有实例的记录查看对应流程详情，无实例的记录仍可查看业务数据；第一期发起仍走流程入口。
- 验收：A、B 的数据在同一列表可查询，分别进入正确实例；旧单流程表单和普通业务记录仍可查看。

#### 子表字符外键查询修复（2026-10-08）

- 状态：`✅已完成`。此修复不代表 F-FF-03 整体完成。
- PostgreSQL 子表外键为 `varchar` 时，详情查询原来用 `Long` 类型主记录 ID 比较，导致 `character varying = bigint` 错误。
- 根据已同步的子表外键类型绑定参数；详情查询、编辑时归属校验、清空/删除子表及新增子表统一处理字符与数值外键，保留租户条件。
- 验证：受影响模块及依赖编译通过；2026-10-08 用户确认新建数据、发起、审批及回到业务列表查看记录和流程的完整链路通过，详情查询错误已解决。
- 人工验收：重启后端后重新查看此前报错的记录，确认主表及商品子表回显；编辑子表的已有行、新增行和删除行并保存，重开确认正确；清空子表保存后确认无残留行。

### F-FF-04 已有记录顺序发起

- 增加业务记录与实例关联表，记录表单 ID、业务记录 ID、流程配置/引擎定义 ID、实例 ID及租户信息。
- 从已有记录发起时按表单 ID、记录 ID 和租户范围读取原主表及子表数据，复用业务记录，不新增或修改原业务记录；原记录字段在该模式下只读。
- 流程专属输入随当前流程实例保存，不回写原业务主表或子表；实例关联和快照用于区分原业务数据与本次流程数据，并保留先前流程历史。
- 新建记录发起继续沿用新增业务记录的现有闭环；已有记录发起与新建模式在入口和写入语义上明确区分。
- 将历史单实例关系纳入关联表；同一记录有进行中实例时，不允许再启动另一流程。

### F-FF-08 表单配置页流程管理

- 状态：`✅已完成`。
- 在表单配置页面提供关联流程管理入口；可查看该表单关联的全部流程，从当前表单上下文新建流程配置，并切换关联流程继续配置。
- 新建或修改流程时复用现有流程配置、设计、发布能力；流程与表单仍以 `FlowProcess.formId` 建立唯一权威关联，不额外创建第二套绑定关系。
- 支持同一表单关联多个流程；切换流程时明确当前配置对象，保存后可重新打开并确认各流程仍引用当前表单。
- 本功能面向所有自定义表单；订单主表/子表只是测试数据，不引入订单专属 UI 或业务逻辑。

人工验收：

1. 在表单管理中打开一个自定义表单的全屏配置入口，确认顶部新增“流程配置”，原“数据库表、表单设计、列表设计”切换及上一步/下一步仍正常。
2. 打开“流程配置”，确认列表只显示当前表单关联的流程；无关联流程时显示空状态。新增流程时确认流程分类沿用当前表单分类，表单类型与表单 ID 固定为当前自定义表单；保存后新流程出现在列表并自动选中。
3. 确认可点击列表中的不同流程切换当前项，右侧直接显示所选流程的流程设计；新增/切换均不会影响其他表单的流程。
4. 确认流程设计默认显示在右侧，无需点击“编辑流程”或打开弹窗；选中审核节点后，右侧基础设置、审批规则和表单权限内容均正常显示。可通过顶部步骤切换基础信息、流程设计和扩展配置，修改节点并发布后仍留在表单配置页，流程列表刷新且仍选中当前流程。
5. 在“流程配置”页点击“保存表单配置”，确认表单配置保存成功且全屏配置仍保持打开；关闭后重新打开，确认关联流程及已发布的流程配置仍可查看。

- 2026-10-07：用户确认 F-FF-08 人工验收通过，状态更新为 `✅已完成`。

### F-FF-05 统一流程操作入口

- 业务数据页保留普通新增、查看和编辑；补充“保存并发起”“发起流程”“流程记录”。
- 只有一个可用流程时直接显示具体操作名称，多个流程时选择；不增加简单/高级两种入口。

### F-FF-06 共享表单差异与快照

- 同一表单在不同流程中的显示、编辑、必填差异，先复用现有节点字段配置。
- 审批历史读取提交时的表单配置及数据快照，业务页面展示当前业务数据；先做轻量快照。
- 已有记录发起时，历史快照保留发起时读取的原主表/子表数据；该流程新增的专属输入单独归属于当前实例，不覆盖原业务记录。

- 业务明确需要时，再讨论并行流程的数据修改冲突、状态展示及自动选择条件。

## 决策与兼容边界

- **配置关系：** 一张表单可被多个流程引用；第一期一个流程继续引用一张表单，以 `FlowProcess.formId` 为唯一配置依据。
- **业务范围：** 本方案使用自定义表单和业务记录作为通用概念；测试订单表不代表订单领域专用实现。
- **运行关系：** 第一阶段不同新建发起创建不同业务记录，每条记录对应一个实例，因此暂保留业务表的单个 `flow_instance_id`。已有记录多实例及历史关联在 F-FF-04 实现，关联表作为可追踪多次流程的关系依据。
- **已有记录发起：** 原业务主表和子表只读并保留快照；本次流程专属数据存于当前实例，不回写原业务记录。新建模式继续创建业务记录。
- **旧数据：** 暂保留 `FlowForm.flowProcessId` 字段用于过渡，不再维护为权威关系；旧绑定与流程侧 `formId` 不一致时提示管理员处理，不自动覆盖配置或修改业务数据。
- **推进方式：** 按页面＋后台小闭环实施。先验证核心复用，不扩大到索引、复杂迁移或完整安全/测试体系；保留已有安全和幂等边界，执行最小充分验证。
